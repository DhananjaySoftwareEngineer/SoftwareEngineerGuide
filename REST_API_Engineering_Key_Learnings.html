REST API Engineering: My Key Learnings

Notes from a project where I explored REST API development in depth and questioned every small design decision: API contracts, HTTP status codes, asynchronous communication, authentication and background processing.

Small choices can affect security, scalability, maintainability and downstream systems. These are the lessons that stayed with me.

Sometimes the biggest learning comes not from writing code, but from questioning every small design decision behind it.

1API-first development with OpenAPI

Before implementing a REST API, define its contract. In our project this meant writing an openapi.yaml file along with matching test.http files.

An OpenAPI contract defines the API's structure:

  • URL patterns and HTTP methods
  • Path parameters, query parameters and headers
  • Request payloads and response schemas
  • Required and optional fields
  • Expected HTTP status codes
Why it mattersThe contract is a clear agreement between API consumers and providers, settled before implementation begins.

2Designing RESTful API endpoints

A REST API should communicate its intent through its HTTP method and a resource-oriented URL.

  • Represent resources with nouns, not verbs.
  • Collection endpoints typically use plural nouns; individual resources are identified by their IDs.
  • Version your API so it can evolve while staying compatible with existing consumers.

The URL structure we followed:

/api/{version}/{area}/{resource}/{endpoint}

The exact structure depends on a project's conventions. Consistency and clarity are what matter.

3Catch-all routing in Minimal APIs

A catch-all route captures the remaining path segments, so one route can handle many function paths:

{enterpriseId}/{siteId}/{productId}/{**functionPath}

The {**functionPath} parameter swallows everything after productId. This helps when an API must support flexible downstream function paths without a separate route for every variation.

Trade-offFlexible routing needs careful validation and authorization so that only permitted operations can be invoked.

4My first hands-on experience with .NET Minimal APIs

Minimal APIs define HTTP endpoints concisely, without the traditional controller-based structure.

RouteGroupBuilder group = app.MapGroup("/items")
    .WithTags("Items")
    .AddEndpointFilter<ValidationFilter>();

Once the group is configured, define endpoints with MapGet, MapPost, MapPut, MapPatch and MapDelete.

Dependency injection works directly through endpoint parameters, including services marked with [FromServices]. Endpoint definitions stay short while still supporting validation, DI and other cross-cutting concerns.

5Request parameters, headers and correlation IDs

Defining a single request parameter takes real thought. Ask:

  • Is it mandatory or optional?
  • Can it be null?
  • Should it be a string, a GUID or another type?
  • What happens if the client does not provide it?
  • Should the server generate a value when it is missing?

Where should a parameter go? Path, query, header or body

Once you know what a parameter is, decide where it travels. The HTTP request has four places for data, and each has a different purpose. Choosing the wrong one hurts caching, security, logging and readability.

LocationWhat it expressesUse it whenExample
PathWhich resourceThe value identifies the resource. It is required, and without it the URL means something else./orders/{orderId}
QueryHow to view the resource or collectionThe value filters, sorts, pages, searches or shapes the result. It is usually optional.?status=pending&page=2
HeaderMetadata about the requestThe value describes the request itself, not the business data: auth, tracing, content negotiation, idempotency, concurrency.Authorization: Bearer ...
BodyThe data being sentYou are creating or changing something (POST, PUT, PATCH), or the payload is large or nested.{ "name": "..." }

When to use a query parameter

A query parameter refines what you get back from a resource or collection without changing which resource it is. /orders is still the orders collection; the query string only decides which slice of it you see.

  • Filtering: ?status=pending&customerId=42
  • Sorting: ?sort=createdAt&order=desc
  • Pagination: ?page=2&pageSize=20 or ?cursor=abc
  • Searching: ?q=laptop
  • Shaping the response: ?fields=id,name or ?include=items

Why it fits: GET requests have no body by convention, so query parameters are how a GET carries options. Because they are part of the URL, they are visible, bookmarkable, shareable and part of the cache key. Two different query strings are treated as two different cacheable responses.

AvoidDo not put secrets (tokens, passwords, API keys) in the query string. URLs end up in browser history, server and proxy logs, analytics and referrer headers. Do not use query parameters for required identifiers (use the path) or to name an action such as ?delete=true (use the HTTP method).

When to use a header parameter

A header carries information about the request rather than about the business data. It is typically cross-cutting: it applies to many or all endpoints and is often handled by middleware, an API gateway or a filter before your endpoint code runs.

  • Authentication: Authorization: Bearer <token>
  • Content negotiation: Content-Type, Accept, Accept-Language
  • Tracing and observability: X-Correlation-Id, traceparent
  • Idempotency: Idempotency-Key so a retried POST does not create a duplicate
  • Concurrency and caching: If-Match, ETag, If-None-Match
  • Request context: values such as a calling application's request ID that every request must carry

Why it fits: headers keep the URL clean and stable, stay out of browsing history and most URL logs, and let every endpoint share the same handling for common concerns. That is why credentials belong in a header and never in the URL.

AvoidDo not hide business data in headers. If a value is something a consumer would reasonably filter by or identify a resource with, it belongs in the path, query or body. Headers are also less visible to consumers, so every custom header must be documented in the OpenAPI contract. Custom headers that vary the response need a Vary header to stay cache-safe.

A quick decision guide

  • Does it identify which resource? Use the path.
  • Does it filter, sort, page or shape the result? Use a query parameter.
  • Is it metadata about the request that applies across endpoints (auth, tracing, idempotency, content type)? Use a header.
  • Is it the data being created or changed, or large and nested? Use the body.
  • Is it sensitive? Never the URL. Use a header or the body.

A useful test: if changing the value gives you a different resource, it belongs in the path. If it gives you a different view of the same resource, it is a query parameter. If it describes how the request is being made, it is a header.

How it looks in a Minimal API

app.MapGet("/orders/{orderId:guid}", (
    Guid    orderId,                                          // path: which order
    [FromQuery] string? include,                          // query: optional, shapes the result
    [FromHeader(Name = "X-Correlation-Id")] Guid? correlationId // header: request metadata
) => Results.Ok());

In the OpenAPI contract, the same choice is declared with the in field:

parameters:
  - name: orderId
    in: path          # required, identifies the resource
    required: true
    schema: { type: string, format: uuid }
  - name: status
    in: query         # optional filter
    required: false
    schema: { type: string }
  - name: X-Correlation-Id
    in: header        # request metadata
    required: false
    schema: { type: string, format: uuid }

X-Correlation-Id

A correlation ID traces a request across multiple services and makes troubleshooting distributed systems easier. When an incoming correlation ID is accepted, propagate it consistently through the whole processing flow.

About the X- prefixIt was historically common for custom HTTP headers, but RFC 6648 deprecated the recommendation to use it for newly defined parameters. Existing conventions can still be used when a project's contract requires them.

Three identifiers worth knowing

IdentifierWhat it does
CorrelationIdConnects related operations and helps trace a request across services.
CausationIdIdentifies the event or message that caused the current event or operation. In event-driven systems it helps reconstruct the chain of actions behind a particular operation.
ApplicationRequestIdIn our project, identifies the originating application's request context and is a mandatory part of the request contract. Its precise meaning depends on the system's design.

These look like small details, but they are central to observability, debugging and distributed workflows.

6Asynchronous communication using callback URLs

When processing takes seconds or minutes and the client does not need an immediate result, there are two broad options.

Polling

The client repeatedly asks whether the result is ready. Frequent polling creates unnecessary traffic and increases server load.

Callback

The client provides a URL and the server notifies it when processing is done. This reduces polling and is more efficient.

The callback flow

  1. The client submits a request and provides a callback URL.
  2. The server accepts the request and processes it asynchronously.
  3. When processing completes, the server notifies the client through the callback URL.
  4. The client retrieves the result through an appropriate endpoint, if required.
Security considerations
  • Validate callback URLs to prevent server-side request forgery (SSRF).
  • Authenticate callback notifications and protect them against replay attacks.
  • Never expose sensitive information in callback URLs or query parameters.

Detailed, interview-style discussions with a senior architect on these scenarios clarified many questions and deepened my understanding of the trade-offs.

7Validation is not optional

Validate incoming data as early as possible, and enforce the right rules at every relevant trust boundary. That includes:

  • Required fields
  • Data types
  • Allowed values
  • Business rules
  • Authorization requirements
Rule of thumbThe earlier invalid data is rejected, the less unnecessary processing happens downstream.

8Data modelling: required vs. optional fields

One of the most important lessons for me. Marking a field optional instead of required can look like a minor implementation detail. In reality it can change the meaning of the contract and affect database integrity, business logic and downstream consumers.

A good data model clearly defines:

  • Which fields are mandatory
  • Which fields are optional or nullable
  • What each field represents
  • Which constraints must always be satisfied
A practice worth copyingExamine historical database records before deciding how an attribute should behave. Understanding existing data, how it has been used, and how it relates to downstream systems leads to better modelling decisions. It is data-driven analysis and reverse engineering that prevents unintended changes to established behaviour.

10Response design and HTTP status codes

A good response is clear, consistent and minimal. JSON is the common format, and the body should carry only what the client needs. Headers provide useful metadata, such as correlation identifiers.

Status code reference

CodeMeaning
200OK: the request completed successfully.
201Created: a resource was successfully created.
202Accepted: the request was accepted for processing, but processing has not necessarily completed.
204No Content: the request succeeded and no response body is returned.
400Bad Request: the request is invalid or cannot be processed due to a client-side error.
401Unauthorized: valid authentication credentials are missing or invalid.
403Forbidden: the client is not permitted to perform the requested operation.
404Not Found: the requested resource was not found.
408Request Timeout: the server did not receive the complete request in the time it was willing to wait.
409Conflict: the request conflicts with the current state of the resource.
422Unprocessable Content: the content is understood but cannot be processed semantically.
500Internal Server Error: an unexpected server-side error occurred.
504Gateway Timeout: a gateway or proxy did not receive a timely response from an upstream server.

408 vs. 504: a useful distinction

408 Request Timeout

The server did not receive the complete request within the time it was willing to wait.
The problem is on the way in from the client.

504 Gateway Timeout

A gateway or proxy did not receive a timely response from an upstream server.
The problem is between the gateway and the server behind it.
TakeawayThe right status code tells the client what actually happened and helps it respond appropriately.

11Authentication and authorization (with JWT)

Authentication

Who are you?
Failure returns 401

Authorization

What are you allowed to do?
Failure returns 403

Both are essential for secure APIs, particularly when multiple applications and services interact. Security has to be considered throughout the request lifecycle, not added as an afterthought.

About this subsectionThe JWT material below is general knowledge based on RFC 7519 and common .NET practice. It is not specific to any one project.

What is a JWT?

A JSON Web Token is a compact, URL-safe string that carries claims about a user or client. The server signs it, so any later tampering can be detected. A JWT has three parts separated by dots:

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMiLCJyb2xlIjoiYWRtaW4ifQ.Gk3x9...signature-bytes...Zq1
HeaderPayload (claims)Signature

Header

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-2026-01"
}

Payload

{
  "iss": "https://auth.example.com",
  "sub": "user-123",
  "aud": "orders-api",
  "exp": 1760000900,
  "iat": 1760000000,
  "role": "admin"
}
Encoded, not encryptedThe header and payload are only Base64URL-encoded. Anyone holding the token can read them. The signature gives integrity (it was not changed) and authenticity (the right issuer made it), not secrecy. Never put passwords or sensitive personal data in a JWT.

Common claims

ClaimMeaning
issIssuer: who created and signed the token.
subSubject: the user or client the token represents.
audAudience: the API the token is intended for.
expExpiry time (Unix seconds). The token is invalid after this.
nbfNot before: the token is invalid until this time.
iatIssued-at time.
jtiUnique token ID, useful for revocation and replay detection.
role / scopeCustom claims used for authorization decisions.

How the signature is created

The signing input is the encoded header and encoded payload joined by a dot. The issuer signs it with a key:

// HS256 (symmetric: one shared secret)
signature = HMAC_SHA256( secret, base64url(header) + "." + base64url(payload) )

// RS256 (asymmetric: private key signs, public key verifies)
signature = RSA_SHA256_Sign( privateKey, base64url(header) + "." + base64url(payload) )

token = base64url(header) + "." + base64url(payload) + "." + base64url(signature)
ApproachAlgorithmsWho needs which keyBest for
SymmetricHS256The same secret both signs and verifies, so every verifying API must hold the secret.A single application that issues and validates its own tokens.
AsymmetricRS256, ES256Only the issuer holds the private key. APIs verify with the public key, often fetched from a JWKS endpoint.Multiple APIs and services, or a separate identity provider.

Generation: what the server does at login

  1. Authenticate. The client sends credentials (or an authorization code). The server verifies them against its user store or identity provider.
  2. Build the claims. Add sub, iss, aud, and the roles or scopes the user is entitled to.
  3. Set the time limits. Add iat, nbf and a short exp, such as 5 to 15 minutes for an access token.
  4. Sign. Encode the header and payload, then sign them with the secret or private key. Keep that key in a vault such as Azure Key Vault, never in source code.
  5. Return the token. Send the access token to the client, usually with a longer-lived refresh token so the user need not log in again.
// .NET: generating a JWT
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub, user.Id),
    new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
    new Claim(ClaimTypes.Role, "admin")
};

var key   = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretFromKeyVault));
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

var token = new JwtSecurityToken(
    issuer:             "https://auth.example.com",
    audience:           "orders-api",
    claims:             claims,
    notBefore:          DateTime.UtcNow,
    expires:            DateTime.UtcNow.AddMinutes(15),
    signingCredentials: creds);

return new JwtSecurityTokenHandler().WriteToken(token);

Validation: what the API does on every request

The client sends the token in the header Authorization: Bearer <token>. The API does not call the issuer for each request. It checks the token itself:

  1. Extract. Read the Bearer token from the Authorization header and split it into three parts. If it is missing or malformed, return 401.
  2. Check the algorithm. Read alg from the header and accept only the algorithms you expect. Reject none, and never let the token choose how it is verified.
  3. Find the key. Use the kid header to pick the right key. For asymmetric tokens, fetch and cache the issuer's public keys (JWKS).
  4. Verify the signature. Recompute the signature over header.payload and compare it with the one in the token. For RS256, verify with the public key. If it does not match, the token was altered or forged.
  5. Validate the claims. Check the token is within nbf and exp, that iss is a trusted issuer, and that aud is this API.
  6. Build the identity. Create the user principal from the claims. Authentication has now succeeded.
  7. Authorize. Check the roles, scopes or policy the endpoint needs. If the user lacks them, return 403.
CheckProtects againstFailure result
SignatureTampered or forged tokens401
exp / nbfExpired or not-yet-valid tokens, and long-term replay401
issTokens from an untrusted issuer401
audA token meant for another API being reused here401
Role, scope or policyValid users doing things they are not allowed to do403
// .NET Minimal API: configuring validation
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,
            ValidIssuer              = "https://auth.example.com",
            ValidateAudience         = true,
            ValidAudience            = "orders-api",
            ValidateLifetime         = true,
            ValidateIssuerSigningKey = true,
            IssuerSigningKey         = key,
            ValidAlgorithms          = new[] { SecurityAlgorithms.HmacSha256 },
            ClockSkew                = TimeSpan.FromMinutes(1)
        };
    });

builder.Services.AddAuthorization(o =>
    o.AddPolicy("AdminOnly", p => p.RequireRole("admin")));

var app = builder.Build();
app.UseAuthentication();   // who are you? (validates the JWT)
app.UseAuthorization();    // what may you do? (checks the policy)

app.MapGroup("/orders")
   .RequireAuthorization("AdminOnly")
   .MapGet("/", () => Results.Ok());

Best practices

  • Use HTTPS only. A bearer token works for anyone who holds it.
  • Keep access tokens short-lived and use refresh tokens to renew them. A stolen JWT stays valid until it expires, because the API does not ask the issuer on each call.
  • Always validate signature, expiry, issuer and audience. Skipping any one is a common vulnerability.
  • Restrict the accepted algorithms, and reject alg: none.
  • Store signing keys in a vault, and rotate them using kid.
  • Prefer asymmetric signing when several services validate tokens, so they never hold a signing secret.
  • Keep payloads small and free of sensitive data. Authorize from claims, but re-check anything critical on the server.
  • Plan for revocation (for example jti deny-lists, token introspection, or refresh-token revocation), since a self-contained JWT cannot be recalled before exp.
In one lineGeneration is "authenticate, build claims, sign". Validation is "verify the signature, check the claims, then authorize". The API never trusts a token's contents until the signature checks out.

12Azure Service Bus session queues

Session-based messaging was one of the most interesting concepts I met. I had worked with microservices before, but session queues introduced a different way of thinking about service communication.

The scenario

One component was cloud-hosted. Another ran as a Windows Service and did not expose a REST API. How could they communicate reliably? Azure Service Bus offered a messaging-based solution.

How sessions work

  • Messages carrying the same session ID are grouped and processed in order within that session.
  • A receiver accepts a session and processes its messages under session ownership.
  • This suits business workflows whose messages must be correlated and processed sequentially.
Key insightService-to-service communication does not always need a REST endpoint. Messaging is a good alternative when direct HTTP communication is unavailable or undesirable.

13BackgroundService in .NET

.NET BackgroundService runs hosted tasks inside an application. It suits long-running work such as consuming messages, processing queued work, and running scheduled or continuous tasks. Depending on the architecture, it can be an alternative to deploying a separate Azure Function.

Potential benefits

  • Background processing stays close to the application's existing codebase.
  • Dependency injection, configuration and logging infrastructure can be reused.
  • Deployment is simpler when the application already hosts background workers.
  • You get direct control over worker lifecycle, cancellation and error handling.

Choosing between them

Azure Functions

A better fit for event-driven workloads that need managed scaling.

Hosted BackgroundService

A good fit for applications that already run continuously.
LessonSelect the architecture based on the workload, not by choosing a technology by default.

14The biggest lesson: engineering is about the details

The most memorable part of the project was not any single technology. It was the depth of the discussions. Questions like these each revealed another dimension of software engineering:

  • Should a field be mandatory or optional?
  • Should an identifier be a GUID or a string?
  • What happens when a client does not send it?
  • Which status code best represents the outcome?
  • How do we prevent unauthorized callback requests?
  • How should a message be correlated across services?
  • What could break downstream if we change one small part of the contract?

At times the number of considerations can feel overwhelming, and different engineers hold different views on the same decision. What helped was listening carefully, understanding the reasoning behind each viewpoint, and judging decisions against requirements, security, maintainability and system behaviour.

Good software engineering is not just about making something work. It is about making it work correctly, securely, reliably and predictably.

REST APIs may look simple on the surface, but production-ready APIs need careful thought across contracts, data modelling, security, communication patterns, observability and operational behaviour. Every small technical discussion has the potential to become a lasting engineering lesson.
