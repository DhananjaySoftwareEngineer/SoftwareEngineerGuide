First, the big picture

Git keeps your work in four places. Almost every command moves changes from one place to the next.

Working directoryfiles you edit
→git add
Staging areathe next commit
→git commit
Local repositoryyour commit history
→git push
RemoteGitHub, Azure DevOps...
← git pull (fetch + merge) brings remote changes back

Keep this picture in mind. reset moves changes backwards through these places, while merge and rebase combine histories.

01

git status

See what changed before you do anything else

What it does

Shows the state of your working directory and staging area: which branch you are on, which files are modified, which are staged for the next commit, and which are untracked. It only reads, it never changes anything, so it is always safe to run. SAFE

Example

$ git status
On branch feature/login
Your branch is ahead of 'origin/feature/login' by 1 commit.

Changes to be committed:        # staged
        modified:   Login.cs

Changes not staged for commit:  # edited, not added yet
        modified:   README.md

Untracked files:                # new files Git doesn't know yet
        notes.txt

Varieties

CommandWhat it does
git statusFull, readable output with hints on what to do next.
git status -sShort format: two letters per file. Great for a quick look.
git status -sbShort format plus the branch and its ahead/behind count.
git status -unoHide untracked files (--untracked-files=no).
git status --ignoredAlso list files ignored by .gitignore.
git status --porcelainStable, script-friendly output that does not change between Git versions.

Reading the short format: the first letter is the staging area, the second is the working directory.

?? notes.txt      # untracked
 M README.md      # modified, not staged
M  Login.cs       # modified and staged
MM Program.cs     # staged, then edited again
A  NewFile.cs     # new file, staged
D  Old.cs         # deleted, staged
Habit worth buildingRun git status before every add, commit, reset and push. It takes a second and prevents most mistakes.
02

git pull

Bring the latest remote changes into your branch

What it does

git pull is two commands in one: git fetch (download new commits from the remote) followed by git merge (combine them into your current branch). With --rebase, the second step becomes a rebase instead of a merge.

# These two are what "git pull" does together
$ git fetch origin
$ git merge origin/main

Varieties

CommandWhat it does
git pullFetch and merge from the branch your current branch tracks.
git pull origin mainPull a specific remote branch into the current branch.
git pull --rebaseFetch, then replay your local commits on top. Keeps history linear, with no extra merge commit.
git pull --ff-onlyOnly succeed if it can fast-forward. Refuses to create a merge commit, so it is the safest option.
git pull --no-rebaseForce merge behaviour, even if rebase is configured.
git pull --autostashStash your uncommitted changes, pull, then re-apply them.
git pull --allFetch from all remotes.
git pull --pruneAlso remove local references to branches deleted on the remote.
git fetchDownload only, without changing your working files. Use it to look before you merge.

Make rebase the default

git config --global pull.rebase true
Watch outIf you have uncommitted changes that touch the same files as incoming changes, the pull can be blocked. Commit, stash, or use --autostash first. If there are conflicts, fix the files, git add them, then continue (git merge --continue or git rebase --continue).
When to use fetch insteadWhen you want to inspect what changed first: git fetch, then git log HEAD..origin/main --oneline to see the incoming commits.
03

git add

Choose what goes into the next commit

What it does

Moves changes from the working directory into the staging area. Only staged changes are included in the next commit, which lets you build clean, focused commits even if you changed many things.

Varieties

CommandWhat it does
git add file.csStage one specific file.
git add a.cs b.csStage several named files.
git add src/Stage everything inside a folder.
git add *.csStage files matching a pattern.
git add .Stage new, modified and deleted files in the current folder and below.
git add -AStage everything in the whole repository (--all).
git add -uStage only modified and deleted files that Git already tracks (--update). Skips new files.
git add -pPatch mode: review each changed chunk and choose y/n. Perfect for splitting one file into two commits.
git add -iInteractive menu for staging.
git add -n .Dry run: show what would be staged, without staging it.
git add -f fileForce-add a file that .gitignore would normally ignore.
git add -N file"Intent to add": record a new file so it shows in git diff before it is staged.

What each option stages

OptionNew filesModifiedDeleted
git add .YesYesYes
git add -AYesYesYes
git add -uNoYesYes

. and -A differ only in scope: . is limited to the current directory, -A covers the whole repo.

Undo a mistaken add

git restore --staged file.cs    # unstage a file (keeps your edits)
git reset file.cs               # older equivalent
Watch outgit add . is convenient but can stage things you did not mean to commit (logs, secrets, build output). Check with git status, and keep a good .gitignore.
04

git commit

Save a snapshot of your staged changes

What it does

Takes everything in the staging area and records it as a new commit in your local repository, with a message explaining why. Commits are your project's checkpoints, and nothing leaves your machine until you push.

Varieties

CommandWhat it does
git commitOpen your editor to write the message.
git commit -m "message"Commit with an inline message.
git commit -m "title" -m "details"Subject line plus a separate body paragraph.
git commit -aAuto-stage all tracked modified and deleted files, then commit. New files are not included.
git commit -am "message"The shortcut for the two above.
git commit --amendRewrite the last commit: change its message and/or add newly staged changes.
git commit --amend --no-editAdd staged changes to the last commit, keeping its message.
git commit --allow-empty -m "msg"Create a commit with no changes (for example to retrigger a pipeline).
git commit --no-verifySkip pre-commit hooks. Use sparingly.
git commit --fixup <hash>Create a fix commit that rebase -i --autosquash will fold into the target commit.
git commit -SSign the commit with your GPG/SSH key.
git commit -vShow the diff inside the editor while you write the message.

Writing a good message

  • Short subject (about 50 characters), in the imperative mood: "Add login validation", not "Added" or "Adds".
  • Explain why in the body when it is not obvious. The diff already shows what.
  • One logical change per commit.
git commit -m "Add input validation to login endpoint" -m "Reject empty usernames and passwords before hitting the database."
Amend rewrites history--amend replaces the last commit with a new one (new hash). If that commit was already pushed to a shared branch, do not amend it: make a new commit instead.
05

git push

Publish your local commits to the remote

What it does

Uploads commits from your local branch to the matching branch on the remote repository so your team can see them. Git accepts the push only if it is a fast-forward, meaning the remote has no commits you lack.

Varieties

CommandWhat it does
git pushPush the current branch to its upstream.
git push origin mainPush a named branch to a named remote.
git push -u origin feature/xPush and set the upstream, so later you can just type git push and git pull. Use it for a new branch's first push.
git push origin local:remotePush a local branch to a differently named remote branch.
git push --allPush all local branches.
git push --tagsPush all tags.
git push --follow-tagsPush commits plus the annotated tags that point at them.
git push --dry-runShow what would be pushed without pushing.
git push origin --delete feature/xDelete a branch on the remote.
git push --force-with-leaseForce-push, but only if nobody else has pushed since you last fetched. SAFER FORCE
git push --forceOverwrite the remote branch no matter what. DANGEROUS

When the push is rejected

$ git push
 ! [rejected]        main -> main (fetch first)
# The remote has commits you don't have. Bring them in, then push again:
$ git pull --rebase
$ git push
Force-pushingForce-pushing rewrites the shared history and can erase teammates' work. Never force-push to main or any shared branch. On your own feature branch after a rebase or amend, prefer --force-with-lease over --force.

Before the reset commands: the three modes

git reset moves your branch pointer (HEAD) to another commit. The mode decides what happens to the staging area and your files.

ModeHEAD movesStaging areaWorking filesRisk
--softYesKept (still staged)KeptSAFE
--mixed (default)YesReset (unstaged)KeptSAFE
--hardYesResetReset (changes lost)DESTRUCTIVE
Before:  A --- B --- C --- D   (HEAD at D)

git reset <mode> B   moves the branch back to B.
 --soft   the changes from C and D stay STAGED
 --mixed  the changes from C and D stay in your files, UNSTAGED
 --hard   the changes from C and D are DISCARDED
06

git reset --soft

Undo a commit but keep every change staged

What it does

Moves HEAD to another commit and leaves the staging area and your files untouched. The commit disappears from history, but all of its changes are sitting in the staging area, ready to be committed again.

Example

$ git reset --soft HEAD~1      # undo last commit, keep changes staged
$ git status
Changes to be committed:
        modified:   Login.cs      # still staged, ready to recommit

When it is useful

  • You committed too early or with a poor message, and want to recommit properly.
  • You forgot to include a file: unstage nothing, add the file, commit again.
  • You want to combine several small commits into one (see the next section).

Varieties

CommandWhat it does
git reset --soft HEAD~1Undo the last commit, keeping changes staged.
git reset --soft <hash>Move back to a specific commit.
git reset --soft origin/mainCollapse all your local commits since the remote branch back into the staging area.
git reset --mixed HEAD~1Same idea, but the changes come back unstaged. This is the default if you write just git reset HEAD~1.
Why it is safeNo file content is lost, and you can always undo the reset itself with git reset --soft ORIG_HEAD or by finding the old commit in git reflog.
07

git reset --soft HEAD~n

Undo the last n commits and squash them into one

What it does

The same soft reset, but stepping back n commits at once. Every change from those n commits ends up staged together, so you can create a single clean commit. This is one of the simplest ways to squash.

Understanding HEAD~n

ReferenceMeaning
HEADThe latest commit on your current branch.
HEAD~1 (or HEAD^)One commit before HEAD (the parent).
HEAD~3Three commits before HEAD.
<hash>A specific commit by its ID (find it with git log --oneline).

Squash the last 3 commits into one

$ git log --oneline
a1b2c3d Fix typo
e4f5a6b WIP validation
9c8d7e6 Start login feature
5f4e3d2 Previous work             # keep this one

$ git reset --soft HEAD~3
$ git commit -m "Add login feature with validation"

$ git log --oneline
7a8b9c0 Add login feature with validation
5f4e3d2 Previous work

Varieties

CommandWhat it does
git reset --soft HEAD~2Undo the last 2 commits, keep all their changes staged.
git reset --soft HEAD~5Undo the last 5 commits, ready to recommit as one.
git reset --soft HEAD~3 && git commit -m "..."Squash the last 3 into a single commit in one line.
git log --oneline -n 5Check how many commits to go back before you reset.
Already pushed?If those commits are on a shared remote, do not rewrite them. Either use git revert to undo them safely, or (on your own branch only) squash locally and git push --force-with-lease.
08

git reset --hard

Throw away commits and local changes completely

What it does

Moves HEAD to the target commit and makes both the staging area and your working files match it exactly. Uncommitted changes to tracked files are wiped out. DESTRUCTIVE

Varieties

CommandWhat it does
git reset --hardDiscard all uncommitted changes and return to the last commit (same as --hard HEAD).
git reset --hard HEAD~1Delete the last commit and its changes entirely.
git reset --hard HEAD~3Delete the last 3 commits and their changes.
git reset --hard <hash>Jump the branch and files to an exact commit.
git reset --hard origin/mainMake your local branch identical to the remote one. Local commits and changes are dropped.
git reset --hard ORIG_HEADUndo the previous reset or a bad merge or pull, by returning to where HEAD was before.

Typical use: "my branch is a mess, make it match the remote"

$ git fetch origin
$ git reset --hard origin/main

What --hard does not touch

Untracked files (brand-new files never added) survive a hard reset. To remove those too, use git clean:

$ git clean -nd      # preview what would be deleted (dry run)
$ git clean -fd      # delete untracked files and folders

Recovering after a mistake

If you reset away committed work, Git still remembers it for a while in the reflog:

$ git reflog
7a8b9c0 HEAD@{0}: reset: moving to HEAD~2
e4f5a6b HEAD@{1}: commit: Add validation   # the lost commit
$ git reset --hard e4f5a6b
No safety net for uncommitted workChanges that were never committed or stashed cannot be recovered after --hard. Run git status and git diff first. If you only want to discard changes in one file, use the gentler git restore file.cs.
09

git merge

Combine another branch into the one you are on

What it does

Brings the commits of another branch into your current branch. First switch to the branch that should receive the changes, then merge the other one in.

$ git switch main
$ git merge feature/login

Two kinds of merge

Fast-forward

Used when main has not moved since the branch was created. Git simply moves the pointer forward. No merge commit. 
main     A---B
              \
feature        C---D

after: A---B---C---D  (main)

Three-way merge

Used when both branches have new commits. Git creates a merge commit with two parents. 
main     A---B---E-------M
              \         /
feature        C---D---

M = merge commit

Varieties

CommandWhat it does
git merge featureMerge, fast-forwarding if possible.
git merge --no-ff featureAlways create a merge commit, even if a fast-forward is possible. Keeps the branch visible in history.
git merge --ff-only featureMerge only if it can fast-forward, otherwise stop.
git merge --squash featureStage the combined changes as one set, without a merge commit. You then run git commit yourself.
git merge --no-commit featureMerge but pause before committing, so you can inspect the result.
git merge -m "message" featureProvide the merge commit message.
git merge -X theirs featureOn conflicting chunks, prefer the incoming branch (-X ours prefers yours).
git merge --abortCancel a merge in progress and go back to how things were.
git merge --continueFinish the merge after resolving conflicts.

Resolving a conflict

When both branches changed the same lines, Git stops and marks the file:

<<<<<<< HEAD
return total * 0.9;      # your current branch
=======
return total * 0.85;     # the incoming branch
>>>>>>> feature/discount
  1. Edit the file to the final version you want, and delete the markers.
  2. git add file.cs
  3. git commit (or git merge --continue).
Good to knowA merge never rewrites existing commits, so it is safe on shared branches. The trade-off is a history with extra merge commits.
10

git rebase

Replay your commits on top of a new base

What it does

Takes the commits on your branch, sets them aside, updates the branch to the tip of another branch, and re-applies your commits one by one on top. The result is a clean, straight-line history, as if you had started your work from the latest code.

$ git switch feature/login
$ git rebase main

Before:   A---B---C  (main)
               \
                D---E  (feature)

After:    A---B---C  (main)
                   \
                    D'---E'  (feature)   # new commits, new hashes

Varieties

CommandWhat it does
git rebase mainMove your current branch onto the latest main.
git rebase origin/mainRebase onto the remote version of the branch.
git rebase -i HEAD~nInteractive rebase: edit, reorder, squash or drop the last n commits.
git rebase --onto new old branchMove a range of commits to a different base (for a branch created from the wrong place).
git rebase --continueCarry on after resolving a conflict.
git rebase --skipSkip the commit that is causing the conflict.
git rebase --abortCancel and return to the state before the rebase.
git rebase --autostashStash uncommitted changes, rebase, then restore them.
git rebase -i --autosquashAutomatically arrange fixup! commits next to the commits they fix.
git pull --rebaseFetch and rebase your local commits in one step.

Interactive rebase actions

$ git rebase -i HEAD~4

pick   9c8d7e6 Start login feature
squash e4f5a6b WIP validation        # melt into the previous commit, merge messages
fixup  a1b2c3d Fix typo              # melt into the previous commit, drop this message
reword 3b4c5d6 Update docs          # keep the change, edit the message
ActionEffect
pickKeep the commit as it is.
rewordKeep the commit, change its message.
editPause at this commit so you can change its content.
squashCombine with the previous commit and merge the messages.
fixupCombine with the previous commit and discard this message.
dropDelete the commit.
The golden rule of rebaseNever rebase commits that other people already have (shared or public branches). Rebase rewrites history, giving commits new hashes. Rebase your own local or feature branch, and after a rebase of a pushed branch use git push --force-with-lease.

Merge vs rebase

MergeRebase
HistoryPreserves the true history, with merge commits.Linear and tidy.
Rewrites commits?NoYes (new hashes)
Safe on shared branchesYesNo
ConflictsResolve once.May resolve per commit.
Best forIntegrating a finished feature into main.Updating your feature branch with the latest main, and cleaning commits before a pull request.

I want to...Use

Discard edits in one filegit restore file
Fix the last commit's message or add a forgotten filegit commit --amend

Undo last commit, keep changes unstagedgit reset HEAD~1

Tidy, reorder or squash commits selectivelygit rebase -i HEAD~n

Habits that keep you safe

  • Run git status before and after every important command.
  • Commit often in small, focused steps, because committed work is almost always recoverable.
  • Rewrite only local history. Once it is shared, use revert and merge.
  • Prefer --force-with-lease over --force.
  • Before a risky operation, make a backup branch: git branch backup.
